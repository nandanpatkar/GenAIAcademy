Dynamic Routing Design
Lesson objectives

In this lesson, you will do the following:

Explore the use of a centralized configuration database.

Lesson introduction

Key routing decisions occur before a call is answered. Amazon Connect uses tools such as data, real-time statistics, business rules, and calculated attributes to help inform these routing decisions. Contact center administrators can use these tools to implement efficient routing strategies, enhance customer experiences, and achieve improved business outcomes.

Baseline routing design

It is important to develop a baseline (bootstrap) pre-routing flow that runs across all contacts across similar contact center lines of business. The bootstrap flow sets the foundation for all flows and customer experiences in the contact center. You can manage your routing in a modular way and use a centralized configuration database that provides key settings for your flow.

For example, you can use Amazon DynamoDB as the configuration database where you store a set of settings for your workloads. When a contact calls the contact center, the active flow uses the dialed phone number to retrieve the configuration for that specific workflow. The returned configuration values are then used as dynamic attributes for the following flows.

Bootstrap architecture

In this sample architecture, a contact reaches out to an Amazon Connect contact center, and a bootstrap flow module is activated. The flow module uses an Invoke AWS Lambda function flow block to search the configuration by using the dialed phone number. The Lambda function retrieves configuration data from a DynamoDB table.

The following are examples of configuration settings you can use as part of a bootstrap flow.


did
This setting represents the phone number dialed by the contact. This value is used as a search key to retrieve the rest of the values stored in the configuration table.


is_emergency
This setting is the emergency state flag used to activate an emergency mode experience. You can use this mode for situations when the contact center needs to shut down unexpectedly during open hours.


offer_callbacks
This setting is a flag that indicates whether the following flow actions include a callback offering.


language
This setting represents the configuration value for the language activated to play the emergency message.


emergency_message
This setting contains an emergency message to play for contacts when the emergency mode is activated by the is_emergency flag.


default_greeting
This setting contains the standard greeting message played for all incoming contacts.


default_recording
This setting contains a standard message that informs the contact about the call recording.


out_of_hours
This setting contains the message that informs the contact about the options available outside operating hours.

These dynamic configuration settings help shape the customer's experience when they are interacting with your contact center. By keeping the configuration in one place, you can reduce the time required to maintain multiple flows while delivering a consistent experience every time.

Handling Unexpected High Contact Volumes
Lesson objectives

In this lesson, you will do the following:

Explore queue metrics to inform routing decisions.

Lesson introduction

Contact centers often experience unpredictable volumes of contact interactions. Reasons can vary from marketing campaigns advertising new products to outages in specific areas or changes to the organization's web portal.

In this lesson, you will learn how to handle an unexpected influx of interactions by using real-time queue reporting metrics or offering callbacks. You will also learn how to deflect contacts to communication channels that are less busy at the time of the interaction. 

Using real-time metrics

In Amazon Connect, you can access real-time queue reporting data in flows. You can use queue metrics to inform routing decisions and personalize experiences. By using reporting data, you can dynamically divert contacts to self-service options, callbacks, or other channels. This improves experiences and enhances operational efficiency. To use real-time data in your routing, you first need to retrieve the metrics.

Callbacks

You can use the Amazon Connect queued callback feature to offer callbacks to voice contacts. Contacts can be called back when an agent is available without losing their position in the queue. You can choose to assign the callback to a different queue or leave the contacts in the current queue. Regardless of the option you choose, the contact will not lose their current position in the queue.

When you assign the contact to a specific queue for a callback, you benefit from improved visibility in the number of callbacks to be processed. When you move the contact to a different queue for callback, you need to consider reporting. The reporting metrics for that contact are spread over two separate queues. The initial queue the contact was assigned to will include data for the contact before they were moved to the callback queue. The callback queue will include the metric data for the contact after they were assigned to the callback queue.

To implement callbacks, you use the Transfer to queue flow block. You select the Transfer to callback queue option and configure it according to your requirements.

Callback considerations

You can offer a callback at any point in the experience before the contact is connected to an agent. Common use cases include offering a callback if a queue is at capacity or if a contact has been waiting for a long time. Proactively offering a callback to contacts prevents long wait times. This improves the customer experience and helps optimize costs. 

It is a best practice to develop a flow module or a customer queue flow to determine when to offer callbacks. If the intent is to offer callbacks before the contact is queued, use a flow module. If the intent is to offer callbacks while the contact waits in the queue, the callback experience must be built into a queue flow. The following categories will explore these options in more detail.


Consider operating hours when offering a callback
Callbacks offered near the end of daily operations can be scheduled, but no agents will be available to answer. Similarly, callbacks offered outside the hours of operations will not be offered to agents until they log in. After applying the initial delay, the callback is put into the queue. It remains there until an agent is available to receive the contact.


Check hours of operation
Use the Check hours of operation flow block in Amazon Connect to offer callbacks only during specific hours. This option reduces the likelihood of calls being left in a queue at the end of the day. Stop offering callbacks ahead of the close of business so agents can complete all pending callbacks for that day before logging off.


Consider offering scheduled callbacks
For contacts that have a preferred contact time or that request a callback at end of the day, offering a scheduled callback provides a better experience. Use Amazon Connect Tasks to implement this experience. You can schedule tasks for specific dates and times and include all the originating contact data with the callback number. For advanced scheduled callback use cases, you can build additional logic and functionality with Amazon Connect and other AWS services.


Check metrics and contact data before offering callbacks
Callbacks do not reduce the call volume. Instead, they redistribute the volume over time. You can check the metrics and make callback decisions accordingly. Use contact preferences stored in your customer relationship management (CRM) system or in Amazon Connect Customer Profiles. With this data, you can dynamically filter and sort the options presented to the contact. You can then offer callbacks based on contact preferences and current contact center contact volumes by channel.

Channel deflection

Organizations can deflect voice traffic by updating information on their web portal. By using the GetCurrentMetricData API, developers can check the status of the phone and digital channel queues. With this approach, when call volumes are high, organizations can offer chat and SMS interaction options instead of voice. As contact volumes return to normal parameters, if the wait times are still high, a best practice recommendation is to offer a callback option.

Organizations can also activate call deflection by using self-service options. For example, if a contact calls to check on order status, the routing strategy can offer information about the order. Alternatively, the system can send an SMS with a URL link that helps the caller get access to the required information. This type of contact deflection offers a seamless customer experience while reducing call center costs.

Handling Fraudulent Calls

Lesson introduction

Contact centers occasionally receive fraudulent phone calls. A fraudulent call is when the caller impersonates a contact by using an organization's existing customer phone numbers. Contact centers frequently become targets for social engineering, especially when they use automatic number identification (ANI) as a means of contact identification. Fraudulent calls lead to increased wait times, unexpected costs, or revenue loss for contact centers. In this lesson, you will explore patterns to mitigate the risk of fraudulent calls.

Caller validation

With caller validation, you verify contacts by asking them to enter a one-time password (OTP). The validation flow uses a Lambda function to generate the password and sends the password to the contact through email or SMS. The flow then asks the contact to enter the password they received. If the contact is successfully validated, the flow progresses with the interaction.

Repeat caller identification and deflection

Contact centers encounter situations where multiple interactions originate from the same contact. Most of these repeat interactions are justified and have valid reasons for contacts getting back in touch. However, illegitimate interactions can sometimes occur, and they result in an increase in agent busy time. 

You can implement logic in your flows to handle illegitimate repeat contact situations. One option is to give these contacts a lower priority when you suspect the contact is illegitimate. 

If you suspect contacts are generated by automated systems, you can implement a validation action to test your assumption. For example, ask the contact to enter a randomly generated code. Human contacts can enter the appropriate information, but a machine will find it difficult to follow specific instructions. For illegitimate calls that reach agents, offer an option in the agent application where agents can flag these contacts.

Implement strict guardrails and carefully consider classification criteria for illegitimate contacts. For example, phone number ownership can change. Calls that were previously identified as illegitimate from a specific phone number might not be illegitimate if the phone number ownership changes. 

You can flag and track illegitimate calls by logging basic information in a data store of your choice. You can then analyze and identify patterns based on the frequency of occurrence, contact duration, and interval between contacts.

The following architecture implements contact tracking. In this example, the contacts flagged as illegitimate are stored in a DynamoDB table. You can use this information to further refine your routing decisions. You can implement this logic in flow modules and in the agent applications.

Lesson 5 of 9
Resuming Interrupted Interactions
Lesson objectives

In this lesson, you will do the following:

Explore solutions to resume interrupted multistep processes.
Explore solutions to recover abandoned contacts.

Lesson introduction

Organizations offer customers different options to interact on their channels of choice. Customer interactions can be interrupted by factors beyond the contact center's control. In these circumstances, experience designers can implement logic that retains context, comprehends abandonment reasons, and manages interactions by taking a customer-centric approach. This lesson explores solutions that use previous context to resume interrupted interactions.

Recovering multistep process interruptions

Some of the contact center interactions involve multistep processes that can be disrupted if the contact cannot complete all the necessary steps. An example of such an interaction is making a payment. A payment workflow involves the following steps:

Identify the bill the contact wants to pay.
Specify the amount they want to pay.
Select the account they want the payment to come from.
Specify the date for the payment.
If the contact gets disconnected after step 3, typically they would have to call back, authenticate, navigate the menu, and repeat steps 1–3.

Solutions for mitigating interruptions

To avoid impacting customer trust, organizations must efficiently mitigate the interruption of multistep processes by implementing recovery mechanisms. The following are two potential approaches to recover multistep interruptions:


Track status by using Amazon DynamoDB

Tracking progress by using Amazon Connect Cases
Track the status of each step, and provide details about the data by using a nonrelational managed database such as DynamoDB. Check for interrupted processes for new contacts, and restore the existing context to reduce customer effort and ensure process continuity.



Now that you have learned about how to track status, move to the next tab to learn about the tracking progress.

Both approaches implement logic that checks for open processes or cases as part of the initial bootstrap flow. After the data is retrieved, the flow offers customers the option to resume the action where they left off.

For each call, the flow logic checks whether an inbound call is part of an open process and handles routing accordingly. If no previous open process is found, the flow starts a new tracking process. During the contact interaction, the various steps are tracked in sequence. If the process is interrupted, the next time the contact reaches out, they will resume the process by following the open process branch. If the process continues and all steps are completed, the process is closed.

Considerations

Select a persistent unique identifier for your contact that can be used for the current interaction and future interactions. An example is a unique customer number or account number. In some situations, the phone number related to the contact account might be a viable option. However, the phone number does not always uniquely identify the contact because mobile phone numbers can change owners. 

Another example where the phone number might not be available to use is when contacts use different channels to interact with the contact center. They might initiate a payment over a voice call, get disconnected, and then start a chat. Unless you ask the contact to enter their phone number while using a messaging channel, the phone number is not always available.

If you use the Amazon Connect Cases solution, ensure that you open the case at the beginning of the process and close the case when the process is complete. With this option, you can manage multistep processes at scale without the use of any additional AWS services. When the contacts return, query for open cases, and use the data returned in the case fields to continue the process from the point where the process was interrupted.

Configure case block options: Link contact to case and Request Fields, such as Case Reason, Customer, and Status.

With this approach, you can reduce customer effort and ensure a seamless contact issue resolution.

Recovering abandoned contacts

During some interactions, contacts disconnect after waiting in the queue for longer than expected periods of time. The experience can be frustrating for contacts, and it can be damaging for a business both from a customer satisfaction and a business revenue perspective. 

With Amazon Connect, organizations can define business rules to recover contacts who abandoned while waiting in the queue. To learn about the recommended steps for implementing recovery solutions for abandoned contacts, choose the following tabs.

From a reporting standpoint in Amazon Connect, any call that enters a queue and never connects to an agent is an abandoned call. This definition is correct from a reporting standpoint, but organizations are more selective when deciding which abandoned calls to recover.

Regardless of the approach, the key steps are to recognize the abandoned call, store the customer's data, and call them back. Organizations should also have a mechanism to remove the tracking if the customer calls back on their own.

Architecture of a callback flow

In this example architecture, the organization processes contact records sent from Amazon Connect to the configured Amazon Kinesis Data Streams. A Lambda function is invoked when a record or batch of records enters the stream. The function identifies if the record was an abandoned call. It then retrieves the configuration data from DynamoDB. This data includes the queue time threshold for an abandoned call. It also includes the flow to use when calling the customer back and the queue to place the call in when requeuing. 

If the function determines the call is recoverable, it places an outbound call by using the StartOutboundVoiceContact API. The customer answers, hears the message, and then chooses if they want to speak with a representative. If so, a callback is set, and the customer is called when an agent is available.

Selecting the contacts to recover

​Selecting the approach to recover contacts
Organizations are selective in determining which abandoned calls to follow up on. When deciding which contacts to recover, organizations typically take into consideration factors such as the following:

The total queue time before the abandon
Self-service attempts before the abandon
The queue the contact was waiting in before the abandon
Contact-specific data, such as a high loyalty level or account status
Current call volumes or the longest wait times at the time of the abandon
Now that you have learned about how organizations select which contacts to recover, move to the next tab to learn about recovering strategies.

​Selecting the approach to recover contacts
After deciding which abandoned calls to track, organizations must determine the most appropriate approach to recover them. There might be valid reasons why a customer disconnected. 



Common approaches considered for recovering abandoned contacts include the following:

Place an outbound call to the contact, and play an automated message. For example, the message might say, "We are sorry you disconnected. If you still need assistance, please press 1, and we will be happy to serve you." This approach uses contact data to determine the original queue time and age of the contact.
Place a callback in the queue on the customer's behalf using the same model as a web-based callback.
Send the contact an SMS message providing a dedicated phone number to call so they can reconnect.

Course summary

In this course, you learned advanced routing strategies in Amazon Connect, focusing on implementing dynamic inbound routing to enhance customer experiences and operational efficiency. You explored foundational routing design principles and how to handle high contact volumes, how to mitigate fraudulent calls, and how to recover interrupted customer interactions.

Concepts
Implementing foundational routing design: Develop a baseline pre-routing flow that runs across all contacts. Use a centralized configuration database, such as Amazon DynamoDB, to store global settings. Implement an administration line to remotely update configurations during emergencies.



Handling high contact volumes: Use real-time queue metrics from the Get queue metrics flow block to inform routing decisions. Offer callbacks by using the Transfer to queue flow block to reduce wait times. Take advantage of channel deflection by offering chat or self-service options based on contact center volumes.

Mitigating fraudulent calls: Implement caller validation by using OTPs sent through secure channels, such as SMS or email. Track incoming calls and log data to identify and deflect repeat callers causing issues.

Recovering interrupted interactions: Implement business task tracking by writing the status of each step in the process and additional data to a tracking database or by using Amazon Connect Cases. Recover abandoned calls by processing contact trace records, identifying abandoned calls based on criteria, and reaching out to customers through outbound calls or callbacks.

Considerations
Security: Implement security measures such as phone number allowlists or PIN-based authentication for remote configuration updates. Carefully handle sensitive information such as OTPs and Social Security numbers.

Operating hours: Consider operating hours when offering callbacks to ensure that agents are available to handle them. Stop offering callbacks ahead of closing time so agents can complete pending callbacks.

Customer experience: Implement guardrails when deflecting calls based on arbitrary information to avoid negatively impacting legitimate customers. Provide clear communication and options when recovering abandoned calls.

Use cases
Emergency activation: Use the administration line to activate emergency mode remotely during unexpected outages or natural disasters, informing customers and offering alternative options.

Channel deflection: Offer chat or self-service options instead of voice calls when inbound contact volumes are high based on real-time metrics from the GetCurrentMetricData API.

Repeat caller identification: Analyze incoming call data to identify and deflect repeat callers causing issues, potentially implementing lower priority queuing or deflection mechanisms.

Recoverable business processes: Track multistep processes such as payments or account updates so customers can resume interrupted interactions without repeating previous steps.

Abandoned call recovery: Identify abandoned calls based on criteria like queue time or customer characteristics. Reach out to customers with outbound calls, callbacks, or SMS messages to reconnect them with agents.
