Lesson 2 of 9
Introduction to Amazon Connect Contact Attributes
Lesson objectives

In this lesson, you will learn to do the following:

Recognize contact attribute types.
Recall common use cases for contact attributes.

Lesson introduction

In Amazon Connect, each interaction with an organization's customers is referred to as a contact. The interaction can be a phone call, a chat, or a task. Each contact has data associated to that specific interaction. This data is stored in Amazon Connect contact records and can be accessed as contact attributes. Some examples include the following: 

Name of the customers
Name of the agent who handled an interaction
Channel type
In the following sections, you will learn the commonly used contact attribute types. You will also explore use cases for contact attributes.

Contact attributes

A contact attribute is a key-value pair that stores custom data associated with an interaction. Contact attributes are associated with the contact record for each interaction.

The key is the name of the attribute, and the value is its content. For example, the key might be City, and the value might be London. 

With contact attributes, you can store and handle contact-related information. The data is available throughout the full journey of the contact. You can use the data to activate a flow, implement a routing strategy, provide contact context to agents, or generate custom reports. 

Contact attribute types

The following are the most common types of attributes used to enhance contact experience. 


System attributes
These contain information about the Amazon Connect instance, in addition to contact identifiers, such as the channel used and the contact’s phone number.


Agent and queue attributes
These provide information about the assigned contact center agent or queue, including the agent name, queue staffing, agents available, and agents busy.


Amazon Lex attributes
You can pass information to and from an Amazon Lex chatbot using contact attributes. Some of the data available in Amazon Lex includes sentiment, intent description, or data collected from the contact while interacting with Amazon Lex.


External attributes
AWS Lambda provides flexible integration ability between Amazon Connect and other AWS services, the customer's own data sources, and third-party applications. Data returned by Lambda functions is stored in external attributes. The external attributes are accessible in Amazon Connect flows.


User defined attributes
Experience designers create user attributes to store data that is relevant for business logic specific to contact center workflows. For example, you can create a contact attribute that stores a specific user selection or preference while interacting with the flows, such as Opt-out of survey.

For a complete list of attributes, navigate to List of Available Contact Attributes and Their JSONPath Reference(opens in a new tab).

Data sources

Some contact attributes are automatically preset by Amazon Connect and the services it integrates with. For example, for voice calls, Amazon Connect stores the phone number that the contact dialed in the Dialed Number system attribute. The contact phone number is stored in the Customer Number system attribute.

Other attributes can be updated using data retrieved from external systems using integration services such as Lambda. The return values from Lambda functions are stored in the External attributes namespace. For example, if the Lambda function implements a contact search by phone number, the return values can be AccountNumber, Balance, and LastPayment. The values can be accessed using references to external attributes, right after the flow invokes the Lambda function.

Data persistence

The data stored in some of the contact attributes is available for consumption for the whole duration of the contact. Some examples include the following types:

System
Media stream
Amazon Lex
User defined
External attributes are populated by Lambda function calls. Every time a Lambda function is invoked, the external attributes are overridden. Agent attributes are set and persist only within the scope of specific flow types, like Transfer to queue or Transfer to agent.

There are use cases where external data populated in the attributes needs to be persistent for the duration of the contact. For example, the contact account number retrieved in the flow needs to be displayed in the agent application. In these use cases, the experience designers must save the value of the external attribute in a user-defined attribute.

After an interaction ends, the contact record is stored in the Amazon Connect instance. User-defined contact attributes are stored in Amazon Connect contact records. Contact records are available within your instance for 24 months.

Flow attributes

Flow attributes are similar to user-defined attributes, but their value does not persist beyond the flow where they are populated. Flow attributes are useful in situations where you don't want to persist the data throughout the contact. A sample use case is a flow where you temporarily store sensitive information like a contact's credit card number to perform a search. By setting a flow attribute, you can pass that attribute as a parameter to a Lambda function. As soon as the flow ends, the value of that attribute is not accessible any longer. 

Common use cases

Contact attributes are used in Amazon Connect flows to personalize user interactions. The following are common use cases where contact attributes enhance user experience.


Queued callback
Use the contact phone number to schedule a queued callback.


Post call survey
Identify which agent interacts with a contact so that a post call survey can be associated with that contact.


Dynamic routing
Identify the number of contacts in a queue to decide if the contact should be routed to a different queue.


VIP treatment
Store look-up data relevant to the contact to route them to the appropriate queue. For example, you could staff the VIP queue with a dedicated team of agents. If the contact is a VIP customer, you can route them to a VIP queue.


Use external data
Use data from a customer interaction with a bot. For example, the type of flowers to order could be data collected for a flower order's bot.

In some flow blocks, you access contact attributes using JSONPath syntax. Encrypt sensitive customer input

To ensure compliance with regulatory programs, such as standards for the payment card industry (PCI), it is critical to secure sensitive data. Therefore, it is critical to encrypt sensitive contact attributes data. By using the Store Customer Input flow block, you can secure sensitive customer information, such as credit card numbers.

Store customer input block
The Store customer input flow block uses public key cryptography for encryption. This is a class of cryptographic protocols that relies on two separate keys: one that is private and one that is public. When configuring Amazon Connect, you first provide the public key. This is the key used when encrypting data. Later, inside the flow block properties, you provide a certificate, which includes a signature that proves you possess the private key. The standard used for this certificate is X.509.

You activate encryption inside of the Store customer input flow block by selecting the Encrypt entry checkbox. Use the encryption key to verify the signature of the certificate used within the flow to encrypt the customer input data. Each Amazon Connect instance is configured with up to two encryption keys active at once to facilitate key rotation.

Store customer input flow block properties.
Accessing the encrypted data

After a customer provides input, the information is stored as a contact attribute alongside the contact. To access the encrypted value, you use the System > Stored customer input contact attribute. To decrypt the encrypted data stored in the Stored customer input attribute, you can use the (opens in a new tab)public key and the corresponding private key. Lesson 4 of 9
External Data Sources
Lesson objectives

In this lesson, you will learn to do the following: 

Explore using data from Amazon Lex and Amazon Connect Customer Profiles as contact attributes.
Explore using contact attributes for integrations through Lambda functions.

Lesson introduction

Contact attributes contain the data you can use to design dynamic customer experiences. For example, you can use the contact’s preferred language from the organization's systems of record. You can anticipate what the user is trying to accomplish and streamline a chatbot interaction. You can use purchase history data to proactively recommend and upsell new products. By analyzing and using contact data, you can create responses and design flows tailored to meet contact expectations and business needs.

In this lesson, you will learn how data from external applications and services helps improve your flows design. 

Get customer input block

The Get customer input flow block in Amazon Connect plays a prompt to ask for a response from the contact. For example, "For sales, press 1. For support, press 2." It offers contacts the option to enter dual tone multi-frequency (DTMF) also called touch-tone or keypad tone input or voice input. The block then branches based on the contact’s input. Some key points about the Get customer input block are as follows:

The block supports voice, chat, and task channels. For the voice and chat channels, the block offers a built-in integration with Amazon Lex. Using this block, you can activate the same chatbot across voice and messaging.
You can configure timeout settings for how long to wait for user input.
The block stores custom input-end keys for DTMF input (for example, a number of sequence of numbers). 
Get customer input block with Amazon Lex


The Get customer input flow block can be configured to collect customer input using Amazon Lex. With this block, contacts are routed to Amazon Lex bots to answer questions and complete self-service operations. After the user intent is fulfilled, the session returns to Amazon Connect with contact attributes containing information about the interaction. These contact attributes are used to make dynamic routing decisions inside your flow to further personalize the customer experience and influence routing logic.

Data available from Amazon Lex

Amazon Lex provides information about contacts as contact attributes. The types of information returned includes the following.


Intent name
This is the user intent returned by Amazon Lex. By gathering the intent name, you can make dynamic routing decisions based on what the contact is asking about. For example, they can be routed to a billing queue if they are asking billing questions.


Intent confidence score
Amazon Lex establishes a confidence of its understanding of the contact’s intent on a 0–1 scale. If Amazon Lex doesn't recognize the contact's utterance confidently, Amazon Connect verifies the confidence score for routing the contact to an agent.


Sentiment label and score
This includes the overall sentiment, which is POSITIVE, NEGATIVE, MIXED, or NEUTRAL, and a numeric sentiment score. The Get customer input block supports sentiment routing. So, each turn of the conversation can route to a branch based on the sentiment of the contact. For example, you can short-circuit the bot experience when sentiment drops to a low score. You can route that contact directly to a queue with an increased priority.


Session attributes
The Get customer input block passes session attributes to Amazon Lex. For example, the block passes the channel that a contact is contacting on as an attribute. Amazon Lex can also return attributes back to the flow, such as data from fulfillment of an intent.


Slots
Amazon Lex slots capture user information inside an intent, such as name, phone number, email address, or custom slot types. Amazon Connect can use slot values to personalize the experience further, such as gathering the contact’s name or a callback phone number.

Use case example: Hotel booking experience

Hotel bedroom with a single bed.
The following is an example of how to use Amazon Lex in a hotel booking experience. When using a Get customer input block, Amazon Connect offers the contact the option to interact with an Amazon Lex bot. User: New York City.

Chatbot: Great, New York City is an exciting destination! When will you be arriving, and how many nights will you be staying?

User: Arriving on June 15 and staying for 4 nights.

Chatbot: Got it. And how many rooms and guests will be staying?

Chatbot: Okay, let me check our available options based on your preferences and past stays (if applicable).

Standard City – King room with city view, $259 per night.

Invoke AWS Lambda function block

IVR designers can use Lambda functions from within flows. With this functionality, they can send and receive data from external systems and databases. Some examples of external systems include the following:

CRM systems
IT service management (ITSM) systems
A Lambda function call can also be used to invoke external APIs. For example, you can call an API to reset a password and use a new password gathered from the contact. Lambda functions are also used to call APIs used by other Amazon Web Services (AWS) services. For example, a flow could invoke a Lambda function that sends an email using Amazon Simple Email Service (Amazon SES) to a contact.

To run Lambda functions as part of flows, cloud administrators must configure Lambda access for the Amazon Connect instance. After the proper permissions are granted, you can use the Invoke AWS Lambda function block. This block passes contact information available in your flow to the Lambda function in the form of function parameters. The parameters can be manually specified or dynamically gathered from contact attributes, such as slot values from Amazon Lex.

The AWS Lambda function returns key-value pairs that are stored as contact attributes in Amazon Connect. You can reference the values returned in the External namespace. For example, $.External.attributeName.

Attributes returned to a flow from a Lambda function are overwritten when another Lambda function is invoked during the flow. Therefore, to use external attributes later in the flow, you must store them in user-defined attributes, using the Set contact attribute flow block.

To learn more, navigate to the Invoke AWS Lambda functions(opens in a new tab) section in the Amazon Connect Administrator Guide.

Flow Design Best Practices
Lesson objectives

In this lesson, you will learn to do the following: 

Recognize best practices for implementing flows.
Identify optimal ways to implement error handling in flows.

Lesson introduction

This lesson contains a collection of recommended best practices to use when you design, create, and support Amazon Connect contact centers. These practices align with the AWS Well-Architected Framework and promote its six pillars. For more information, navigate to AWS Well-Architected Framework(opens in a new tab). The pillars are operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability.

Best practices

There is no right or wrong way to design a flow. Flows are built based on each organization's specific business needs. Experience designers can use the built in flow designer canvas. Developers can use flow language, a JSON-based representation of a series of flow actions, and the criteria for moving between them. With flow language, developers can efficiently update flows when migrating applications from one environment to another. Regardless of how you build flows, applying core design best practices helps ease the operational support while improving user experience. 

To explore flow design best practices, expand each of the following categories. 


Modularized flows
You can create modular flows by breaking down functionality into logical sections. This makes your flows manageable. 



You build your flows as small modules, and then combine them into a complete customer experience. You can use a flow repeatedly in multiple interaction scenarios, thereby reducing regression testing.


Taxonomy
Adopt a standard naming convention for all of your AWS services. This will make it more convenient to build and maintain your flows. Add attributes with the naming convention for facilitating references in the future. Make sure your attribute names do not use spaces or special characters that can impact downstream processing.


Error handling
Ensure all error branches are routed to a block that effectively handles errors or ends contacts so that your contacts retain trust in your contact center. 


Permissions
To maintain a strong security posture, ensure that Amazon Connect has appropriate permissions for all integration points referenced in the flows.


Data security
When you use the Set contact attribute block, make sure you are only storing the data you need. Any user-defined contact attribute you set will be saved as part of the contact.


Monitoring
Use the Set logging behavior block to activate logging of the flow. Disable logging for segments of the flow where sensitive information is collected so that it does not appear in the Amazon CloudWatch monitoring service.


Hours of operation and staffing
Ensure that you insert the Check hours of operation block to verify a contact is within working hours. Add the Check staffing block to ensure that agents are staffed to service a contact. This is necessary before you route the call to an agent.

For additional best practices, navigate to Best Practices for Amazon Connect(opens in a new tab) in the Amazon Connect Administrator Guide.

Error handling

You can use error branches in Amazon Connect flows to handle situations where an error occurs or a condition is not met. Errors might occur for a variety of reasons, depending on the specific block. Some common examples of errors include the following:

Invalid user input
Using dynamic contact attribute values that are not set
Errors from running Lambda functions
When designing the customer experience in a flow, it’s important to design flows in a resilient manner. This ensures that they are able to withstand errors and failures that might occur as part of the design. You will examine some examples of errors in a flow and explore design patterns to handle them.

Handling errors best practices

After understanding why an error occurs in a flow, you need to make a decision about how to handle the error. The following are recommended patterns to use for catching and handling an error inside a flow.


Continue past the error
In some situations, you might be able to proceed past errors without disruption. 

For instance, if the contact information is not available, implement a different experience that does not disrupt the interaction flow. In such cases, it is not necessary to inform customers. You can avoid further customer frustration by maintaining a light and effortless experience and silently advancing past handled errors. 


Gracefully inform the customer and continue
When errors occur, you can create a Flow branch to inform the contact gracefully. For example, consider the situation when an error occurs due to a failed Lambda function used by Amazon Lex. 

A best practice for handling this type of error is to inform the contact that their self-service answers do not reach the external system. The flow does not end. It continues even in the presence of errors. When using error branches, a routing decision can be made to handle this situation. For example, the contact can be routed to an agent in a priority queue.


Gracefully disconnect the customer
If a flow encounters a critical error, it might make sense to gracefully disconnect the customer altogether. Some contact centers choose to put a maximum contact capacity on their queues. Upon hitting this limit, Amazon Connect routes contacts down the At capacity branch of the Transfer to queue block. 



If you want to limit the maximum number of contacts in a queue, you can disconnect the contact after this branch is invoked. Amazon Connect informs the contact gracefully after this branch is invoked before disconnecting. In front of the Disconnect block, use the Play prompt block with the text, "We’re sorry, all of our agents are currently busy assisting other customers. Please try again later."

Summary
Course summary

In this course, you learned about Amazon Connect flow attributes. Take a moment to review the following key concepts before taking the course assessment. 

Contact attributes
Amazon Connect stores data associated with each customer interaction as contact attributes. 



Contact attributes are key-value pairs containing information about the contact, agent, queue, or external data sources. 



Common attribute types include: system attributes, agent attributes, Amazon Lex attributes, and user-defined attributes. External attributes store data from external systems accessed through Lambda functions.



Designers can set contact attributes within flows using the Set contact attributes block. The Check contact attributes block allows branching the flow logic based on attribute values. You can access attribute values using JSONPath syntax like $.Agent.FirstName. 



Sensitive data like credit card numbers should be encrypted using the Store customer input block encryption feature based on public key cryptography.

Accessing external data in flows
There are three ways to access external data in flows:

The Get customer input block integrates with Amazon Lex to enable chatbot interactions within flows. It provides access to data, like intent names, confidence scores, sentiment analysis, and slot values collected during the conversation. 
The Customer Profiles block retrieves customer data from Amazon Connect Customer Profiles using identifiers like phone numbers or emails. 
The Invoke AWS Lambda function block runs Lambda functions to integrate with external systems, databases, and APIs and store returned data in external attributes.
Flows error handling
Design resilient flows to gracefully handle errors and failures. Common errors include invalid user input, unset dynamic attribute values, and failed Lambda function invocations.

 

When errors occur, one option is to continue past the error with an alternate experience path.



In some use cases, you can gracefully inform the customer about the error and continue. In other cases, depending on your workload, you can disconnect the contact after providing an explanatory message. 



Implement error branches to catch and handle different error conditions appropriately.

Flow design best practices
Take into consideration the following best practices when designing flows:

Adopt a modular design approach by breaking flows into reusable components for better manageability. 
Follow a standard naming convention and avoid spaces or special characters in attribute names. Maintain appropriate permissions for all integration points referenced. 
Store only necessary data in attributes to maintain security. 
Use monitoring capabilities and enable logging judiciously to avoid capturing sensitive information. 
Incorporate checks for hours of operation and staffing availability before routing contacts to agents. 
Use contact data to transfer contacts to agents with relevant skill sets.
